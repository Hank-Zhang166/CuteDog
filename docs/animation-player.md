# 真实朝向和逐帧平移契约

播放器读取 `app/src/main/assets/pet3d/manifest.json`，按清单中的原图 SHA-256 从安装包 `pet3d/frame-index.json` 查找对应的独立 WebP。每帧在后台工作线程校验安装字节摘要，精确匹配的镜像由同一线程还原，可从任意帧开始播放。源动作目前包含独立的左右步态、停止/启动与转身桥；完整美术和足锁测量仍须单独验收。

当前资源包含 81 个普通、方向和连接片段，另有 49 条相位恢复桥。行为引擎从 `requestableClipIds` 选择动作。资源摘要与相位入口的合同见[相位清单](phase-manifest-v2.md)。

## 方向元数据

每个 clip 可声明 `heading: "left" | "right"`；省略 `exitHeading` 时出口沿用入口方向。真实转身桥声明不同 `exitHeading`，必须非循环、`interrupt: "never"`，不能在中间帧把朝向当作已经完成。

方向变体声明 `variantOf`，指向存在且不是变体的原动作。例如 `walk_right.variantOf = "walk"`。变体必须有与原动作不同的朝向、独立帧路径和一致的循环类型。`stand_right` 可采用短呼吸循环，帧数不要求与 `stand` 相同。姿态 ID 及每条连接仍须连续；同一姿态 ID 不能对应两个方向。没有方向元数据的旧清单仍可播放，但不会被当作有方向的行走资源。

播放器不通过 ID 后缀猜测方向，不镜像图片，也不添加角色旋转。作者使用固定相机与独立 actor yaw 渲染左右动作。旧的 180° `turn/back_stand/turn_back` 仍按其真实姿态路径播放。

## 实测平移元数据

允许平移需要同时声明：

- `canTravel: true`：作者已批准此动作的足锁平移；省略或 false 均禁用，即使已经附带测量数组。
- `projectedTravel`：长度必须等于真实帧数，每项为当前帧 `i → next` 的非负画幅宽度比例。禁止字符串、负数、非有限值和超过一个画幅宽度的单帧位移。
- `travelUnits: "canvas_width_fraction"`：没有像素单位或 384/512 分辨率假设。
- 相同且明确的入口/出口 `heading`：转身桥不允许推进窗口。

`sampling` 默认是旧资源的 `inclusive_endpoints`，非循环末项必须为 0。新资源可明确使用 `interval_starts`：保留含终点的源采样供审计，发布时删除最后的重复端点及其 0 位移，最后一个运行帧到下一片第 0 帧的真实推进量必须保留。跨片姿态和朝向须一致。当前 2.5D 试验源的 start/walk/stop 分别为 37/25/31 个源采样，对应 36/24/30 个运行帧；这些数量不是已装入 APK 的资源承诺。

启用某个移动片段还要求：同朝向站姿、站姿到该片段的启动路径，以及该片段到站姿的完整停步路径都存在逐帧测量；有正位移的各片段均须明确获准，静止桥使用明确的全 0 数组。仅批准 walk 循环而没有 start/stop 测量会拒绝整份清单。数组来自实际接触及画面投影测量，不按 `walk/run` 等名字填速度。`play_ball`、`treat` 等道具互动不启用平移。

## 原生调用

`FrameClipPlayer` 提供：

- `requestHeading(sign: Int): Boolean`：只接受 -1 / +1，并沿已声明路径重排同一个逻辑动作。期望方向与实际方向分离：旧方向的当前周期和停步仍消费实测步幅，真实换向桥自身无位移，桥完成后才使用新方向。同方向重复提示不会覆盖用户/AI 互动。
- `request(clipId)`：逻辑 ID 按期望方向选真实变体；显式变体 ID 保持精确请求。互动请求可以覆盖排队方向，沿合法路径回到其真实入口姿态。
- `canonicalClipId`：供 PetBrain 使用，例如真实 `run_right` 映射为逻辑 `run`；转身桥保持其真实 ID，不能提前完成 pending 行走目标。
- `canTravel` / `travelHeading`：根据当前真实片段的已批准位移和实际朝向，且须活动、当前帧就绪、无加载错误或空间阻断。排队中的互动或方向目标不会抹去旧方向尚在播放的步幅。不可平移时 `travelHeading` 为 0。
- `stoppingTravelFraction`：当前帧至本周期结束，再沿同朝向合法路径停至站姿的剩余实测距离；供宿主预留刹停空间。`requestStop()` 请求该站姿而非提前冻结移动片段。
- `authoredTravelDeltaFraction`：上一 tick 成功提交真实帧产生的**有符号**位移比例。每次 tick 开始清零；暂停、未准备好、解码停顿、换向桥与非移动动作均为 0。读取不会自动消费；宿主每 tick 只使用一次，不能累加重复读取。

宿主调用 `tick(deltaSeconds, approveTravel, approveEntry)`。跨片进入移动路线前，`approveEntry(heading, fraction)` 核实包含完整停步的水平安全段，向前看穿全 0 位移的启动/转身桥；空间不足时拒绝规范动作目标并保持安全回程，不先进入无法停下的腿位。在真实下一帧已解码后，`approveTravel` 再核实**完整**的有符号单步是否有空间；拒绝时不提交画面或位移，并输出 `travelBlockedReason`，以 250ms 间隔重试。允许时将本次 `authoredTravelDeltaFraction × 实际绘制宽度 × spatialDepth` 应用到窗口，再显示新帧。必须消费本次已提交增量，即使下一片已经进入静止站姿、当前 `canTravel` 因而变为 false。如果“实际绘制宽度”已经包含深度缩放，不要重复乘；也不要乘 deltaSeconds 或替换真实的 0 位移。

`PetView` 把每次实际换帧的比例立即乘 `min(width,height) × spatialDepth`，交给 `AuthoredTravelAccumulator`，再在本次主线程回调内同步调用 `OverlayService.consumeAuthoredMovement`，窗口更新后才 invalidate 新位图，最后才选择下一行为。约 20Hz 的路线回调不再次消费位移。累计器每次消费清零；没有新帧的 0 增量不会覆盖此前未消费部分。新互动/方向请求保留已经提交的旧方向增量；暂停、触摸/拖动、气泡、配置及锁定会清空预算。超过 250ms 的未消费积压会丢弃，恢复时不会突跳补偿。

路线规划预留当前周期剩余距离、完整停步片段距离与三个实测帧的规划余量，进入新移动片段或循环末帧回到第 0 帧时再次核实整轮加停步的空间。安全站姿本身必须没有正位移。没有 heading 的旧静止姿态可沿全零位移路径回站，拒绝新行走时不会反复保留被拒目标。规划目标可略被停步越过，但有效区域和障碍是硬边界：不能裁短最后一步却继续播放新腿位。配置骤变、交互遮挡或空间不足时，逐帧预检暂停画面和位置，诊断会说明阻断；这是一种明确的安全暂停，不宣称完成了自然停步。清单中没有获准的 start/stop 数据时不启用平移。

连续帧专用调度使用 `Choreographer.frameTimeNanos` 与 `FrameCadence` 的下一实际边界，并扣除回调已耗时。24fps 在模拟的 60Hz 时钟上对应交替 2/3 个 vsync，12fps 对应 5 个；不再固定使用 31ms/70ms 定时。等待解码时只检查缓存、保持原帧，不执行行为选择/电池查询或反复 invalidate；加载错误和清单未就绪会降频。旧图集的原定时保持不变。纯 Kotlin 时钟测试验证这种调度计算及暂停重置，不等于已经测量 Android GPU 显示时间、真实连续帧流畅度或设备掉帧。

当前契约仅测量**屏幕水平**推进，连续帧模式只选择同高度、有效且无遮挡的水平安全段，不把水平标量沿任意二维路线分摊。未来须由资源提供真实 `projectedTravelVector` 等向量测量并同步升级验证与播放器，才可支持相应斜向/纵向脚步；目前没有伪造该字段。用户拖动及拖动后的吸边仍是独立定位行为，不受脚步 `canTravel` 开关限制。旧图集预览保留原有行为；`play_ball` 与 `treat` 即使误声明了可移动目标，悬浮层也保持其原地互动。

`DirectionalClipTest` 使用明确的控制流夹具覆盖完整换向、桥中重定向、互动期间旧步幅继续、启动/停步路径测量缺失拒绝、停步距离、空间拒绝不提交、跨片末项、规范 ID、未批准位移关闭与旧清单兼容。`AuthoredTravelAccumulatorTest` 检查每帧只消费一次、0 增量保留、暂停清空、超时和非法数据。`FrameCadenceTest` 检查 60Hz 上的 24/12fps、可变帧率与回调耗时；`FrameScheduleGateTest` 验证暂停/恢复使旧回调和旧回调尾部失效。夹具不证明美术帧、足锁或设备显示已经验收。
